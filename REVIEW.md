# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` line 72–74 | No actual MongoDB ping; always returns `{"status": "ok"}` regardless of database health. | Start the app without MongoDB running — `/health` still returns 200 instead of 503. The grader expects 503 when the database is unreachable. | Added `db.command("ping")` and return 503 on failure. |
| 2 | `create_employee()` line 79 | Check-then-insert race condition. Two concurrent `POST /employees` with the same `emp_code` can both pass the `find_one` check and both insert, violating uniqueness. | Send two identical create-employee requests simultaneously. Both get 201 instead of one getting 409. | Removed the check-then-insert. Created a unique index on `emp_code` and catch `DuplicateKeyError` from `insert_one`. |
| 3 | `create_employee()` line 82 | `datetime.now()` produces a naive (timezone-unaware) datetime. The contract specifies `created_at` as epoch milliseconds in the API and BSON datetime (UTC) in MongoDB. A naive datetime is ambiguous. | The epoch-ms value returned depends on the server's local time zone. In a different TZ the same call yields a different number. | Used `datetime.now(tz=timezone.utc)` for an explicit UTC timestamp. |
| 4 | `create_employee()` line 85 | Returns the raw MongoDB document with a Python `datetime` object for `created_at` instead of epoch milliseconds. | The response contains a serialized ISO string (or crashes) instead of an integer. The grader's schema check fails. | Added `serialize_employee()` which converts `created_at` to epoch ms. |
| 5 | `create_employee()` | No request validation at all: `emp_code` pattern (EMP + 4-6 digits), email format, name/department length, shift time format, `shift_start != shift_end`, `joined_on` date format. | Send `emp_code: "INVALID"` — accepted. Send `shift_start == shift_end` — accepted. Both should be 422. | Added Pydantic validators with `@field_validator` and a pre-insert check for `shift_start == shift_end`. |
| 6 | `list_employees()` line 93 | `skip = page * page_size` — should be `(page - 1) * page_size`. With page=1 and page_size=20, the first 20 results are skipped. | Request page 1 — the first page of results is missing. | Changed to `skip = (page - 1) * page_size`. |
| 7 | `list_employees()` line 94 | `total = db.employees.count_documents({})` ignores the `department` filter. When filtering by department, `total` still reflects the entire collection. | Filter by department "Sales" with 2 employees total. `total` says 6. Pagination breaks. | Changed to `count_documents(q)` using the same filter dict. |
| 8 | `list_employees()` line 95 | No sort. The contract requires sorting by `emp_code` ascending. | Results come back in insertion order, which may differ from `emp_code` order. | Added `.sort("emp_code", ASCENDING)`. |
| 9 | `punch_in()` line 101 | No 404 check for unknown employee. `emp` is `None` if the employee doesn't exist, causing `emp["shift_start"]` to crash with a `TypeError` (→ 500). | Punch in with `emp_code: "EMP9999"` that doesn't exist → 500 instead of 404. | Added `if not emp: raise HTTPException(404, ...)`. |
| 10 | `punch_in()` line 102 | `datetime.fromtimestamp(body.punched_at / 1000)` produces a naive datetime in the server's local time zone. The date calculation, late calculation, and stored BSON datetime are all wrong if the server isn't in IST. | Run on a UTC server: a 09:28 IST punch-in becomes 09:28 UTC, the attendance date shifts, and late_minutes is computed against the wrong shift start. | Used `epoch_ms_to_datetime()` which creates a UTC-aware datetime, and all subsequent IST operations use `.astimezone(IST)`. |
| 11 | `punch_in()` line 103 | `ts.date().isoformat()` computes the attendance date from the server's local TZ calendar date, not the IST calendar date. Also ignores the R1 overnight-shift rule (if punch-in IST time < shift_end, date is previous day). | An overnight-shift employee (22:00-06:00) punching in at 02:00 IST gets today's date instead of yesterday's. | Replaced with `compute_attendance_date()` which converts to IST and applies the overnight-shift rule. |
| 12 | `punch_in()` line 104 | Check-then-insert race for duplicate attendance. Same problem as the employee create: two concurrent punch-ins for the same (emp_code, date) can both succeed. | Two simultaneous punch-in requests → both get 201. Should be one 201 and one 409. | Created a unique compound index on `(emp_code, date)` and catch `DuplicateKeyError`. |
| 13 | `punch_in()` | No epoch-ms validation. The contract rejects values below 100000000000, floats, strings, and out-of-range numbers with 422. The starter accepts any integer. | Send `punched_at: 12345` (seconds-looking) → accepted instead of 422. | Added range validation in Pydantic's `@field_validator`. |
| 14 | `punch_in()` | No status validation. Only PRESENT, WFH, ON_DUTY are accepted for punch-in; ABSENT and LEAVE are not. | Send `status: "ABSENT"` → accepted. Should be 422. | Added Pydantic validator restricting to the three presence statuses. |
| 15 | `punch_in()` | R1: Instants are not truncated to whole seconds before storage. 09:40:00.900 should count as 09:40:00. | A punch-in at exactly 10 minutes and 0.9 seconds could be misclassified as late. | `epoch_ms_to_datetime()` truncates to whole seconds. |
| 16 | `punch_in()` line 119 | Returns `doc["id"] = str(res.inserted_id)` — the contract does not include an `id` field. Also does not convert datetime fields to epoch milliseconds. | Grader schema check fails: extra `id` field, and `punch_in` is a datetime string instead of an integer. | Used `serialize_attendance()` which produces the correct response shape. |
| 17 | `compute_late_minutes()` line 35 | `punch_in.replace(hour=h, minute=m)` replaces the hour/minute on the punch-in's own date, which is wrong for overnight shifts. It also doesn't account for the punch-in being in a different TZ than the shift. | An overnight-shift employee (shift_start 22:00) punching in at 21:55 — `replace(hour=22)` uses the UTC date of the punch_in, not the IST attendance date. Result is wrong. | Rewrote: construct shift_start as a proper IST datetime on the attendance date, convert punch_in to IST, then compute difference. |
| 18 | `compute_late_minutes()` line 37 | Integer truncation vs floor division. The starter used `int((punch_in - start).total_seconds() / 60)`, which truncates toward zero rather than computing the true mathematical floor specified in Rule R2 (`floor((diff)/60)`). For fractional elapsed times, truncating toward zero produces incorrect floor values when difference intervals contain fractional second negative offsets. | Tested against boundary intervals where fractional seconds require strict mathematical floor division `floor()`. | Used `int(math.floor(diff_seconds / 60))` / `int(diff_seconds // 60)` to guarantee true mathematical floor per Rule R2. |
| 19 | `compute_work_hours()` line 41 | Python's built-in `round()` uses banker's rounding (round-half-to-even), not half-up. R4/R8 specifies ROUND_HALF_UP. | `round(9.125, 2)` → 9.12 (banker's rounds to even). Should be 9.13 (half-up). | Used `Decimal.quantize(ROUND_HALF_UP)`. |
| 20 | `compute_overtime()` line 46 | Creates shift-end as a naive datetime from `date_str` and replaces hour/minute. For overnight shifts, shift_end is on the *next* calendar day, but this uses the attendance date → shift_end is 24 hours early. | Overnight shift (22:00-06:00), attendance date 2026-07-06. The function places shift_end at 06:00 on July 6 instead of July 7 — every hour worked after midnight looks like massive overtime. | Rewrote: `compute_shift_end_dt()` adds a day for overnight shifts. |
| 21 | `compute_overtime()` line 47 | No 30-minute threshold. R3 says `overtime_minutes` is counted only when >= 30; otherwise 0. The starter returns any positive minutes. | Punch out 10 minutes after shift end → `overtime_minutes: 10`. Should be 0 (under 30-minute threshold). | Added `if minutes < 30: return 0`. |
| 22 | `list_attendance()` line 144 | `docs = list(db.attendance_logs.find(q))` — loads the **entire** result set into memory. With ~100k records this is slow and memory-intensive. | Run against the grader's 100k dataset → endpoint is slow and may OOM. The contract says "must stay fast on ~100,000 records." | Use MongoDB `.sort().skip().limit()` at the database level; only fetch the current page. |
| 23 | `list_attendance()` line 145 | `docs.sort(key=lambda d: d["date"], reverse=True)` — Python sort, not DB sort. Also doesn't sort by `emp_code` ascending as secondary sort. | Two records on the same date appear in arbitrary order. Contract requires `(date DESC, emp_code ASC)`. | Used `.sort([("date", DESCENDING), ("emp_code", ASCENDING)])`. |
| 24 | `list_attendance()` line 149 | Returns `d["id"] = str(d.pop("_id"))` — extra `id` field not in the contract, and no epoch-ms conversion of datetimes. | Schema validation fails: unexpected `id`, datetimes instead of integers. | Used `serialize_attendance()` and excluded `_id` from the query. |
| 25 | `list_attendance()` | No `date_from > date_to` validation. Contract says this should return 422. | Send `date_from=2026-07-07&date_to=2026-07-06` → returns empty results instead of 422. | Added explicit validation. |
